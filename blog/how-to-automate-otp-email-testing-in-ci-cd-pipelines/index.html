How to Automate OTP Email Testing in CI/CD Pipelines

The practical guide to testing email verification flows with isolated inboxes, Email APIs, Playwright, Cypress, Selenium, CI workflows, and secure parallel execution.

Quick Answer

To automate OTP email testing in CI/CD, use a dedicated test inbox or Email API instead of a personal Gmail or Outlook account. Generate a unique email address for each test run, trigger the OTP email, retrieve the message programmatically, extract the verification code, and submit it through your browser automation framework.

Create isolated test inbox ↓ Create/register test user ↓ Trigger OTP email ↓ Retrieve email ↓ Extract OTP ↓ Submit OTP ↓ Verify successful authentication

For most CI/CD end-to-end tests, an Email API with isolated inboxes is a practical approach because the test can access messages programmatically without requiring a person to open an inbox.

Key Takeaways

  • Validate the real verification flow: OTP email testing should validate real staging delivery instead of disabling OTP checks.
  • Avoid shared consumer inboxes: Shared Gmail or Outlook accounts introduce delivery lag, MFA blocks, spam filtering, and test collisions.
  • Dedicated Email API: A dedicated Email API provides controlled, programmatic access to test messages over HTTP.
  • Unique mailbox per parallel worker: Give each parallel CI runner a unique email address to prevent cross-worker test flakiness.
  • Programmatic retrieval: Retrieve messages via API or webhooks rather than manual inbox access.
  • Prefer plain-text emails: Plain-text email bodies are significantly simpler and more resilient to parse.
  • Stable HTML selectors: For HTML emails, use data-testid="otp-code" or DOM parsing instead of regex on raw markup.
  • Cover edge cases: Test OTP expiration, resends, invalid codes, and single-use constraints.
  • Secrets management: Store all API keys and test passwords in CI secret vaults.
  • Layer your tests: Use mock SMTP for local unit/integration tests and real staging Email APIs for end-to-end CI suites.
  • Sanitize logs: Keep OTP values, passwords, and magic links out of CI logs, screenshots, and test traces.

What Is OTP Email Testing?

OTP email testing verifies that an application can correctly generate, send, receive, parse, and accept a one-time password delivered through email.

OTP verification is commonly used during:

  • Account registration & onboarding
  • Email address verification
  • Login authentication & passwordless login
  • Password recovery and resets
  • New-device verification challenges
  • Security-sensitive account changes (e.g., billing, email updates)
  • Multi-factor authentication (MFA)

A basic manual flow is simple:

  1. Enter an email address into the web form.
  2. Click Send OTP.
  3. Open the email inbox.
  4. Copy the OTP code.
  5. Enter the OTP into the application.
  6. Continue after successful verification.

Automating this process is more complicated because the OTP exists outside the browser. The browser automation tool (Playwright, Cypress, Selenium) can control the web page, but it cannot automatically know when an external email arrives unless you give the test an email retrieval mechanism.

That creates an additional workflow:

Browser ↓ Application ↓ Email service ↓ Test inbox ↓ Email API ↓ Test runner ↓ Browser

A reliable OTP test therefore needs to coordinate both the browser and the email system. The goal is not simply to check whether an email exists. A useful test must verify that the complete verification journey works end-to-end.

Why OTP Email Tests Fail in CI/CD

Browser automation is generally predictable. A test can execute:

Open page → Enter email → Click button → Check result

Email introduces asynchronous behavior. The application sends a message. The email service processes it. The message becomes available in a mailbox. The test then needs to locate the correct message and extract the correct OTP before the code expires. Any part of that chain can fail.

Common Causes of Test Failure

1. Email delivery is asynchronous

The OTP may not appear immediately. A test that expects the message instantly will fail even though the application eventually sends it successfully.

2. The wrong email is selected

If the inbox contains multiple OTP messages, a test might retrieve an older code. This becomes particularly problematic when a user clicks Resend OTP.

3. Tests share one inbox (Race Conditions)

Suppose four Playwright workers run simultaneously. All four tests use test@example.com:

  • Worker 1 requests OTP A.
  • Worker 2 requests OTP B.
  • Worker 3 requests OTP C.
  • Worker 4 requests OTP D.

If all four read from the same mailbox, there is no guarantee that Worker 2 will retrieve OTP B. The result is a flaky test suite even though the application itself is completely healthy.

4. The OTP expires

OTP codes usually have a short time-to-live (e.g., 5–10 minutes). If the CI runner is delayed under heavy queue loads, the OTP may expire before verification is submitted.

5. Email parsing is fragile

A naive six-digit regular expression (\d{6}) can accidentally match:

  • A tracking or order number
  • A timestamp or date snippet
  • A hex color or CSS value
  • An unrelated phone number or footer identifier in an HTML email

6. Consumer email authentication changes

A test that depends on a personal Gmail or Outlook account breaks over time due to password rotations, mandatory 2FA/MFA challenges, CAPTCHAs, provider rate limits, and spam filtering algorithms.

Best Ways to Test OTP Emails Automatically

There are several approaches to automated OTP email testing:

Approach CI Reliability Speed Best Use Main Limitation
Dedicated Email API + Isolated Inboxes High Fast CI/CD E2E tests External API dependency
SMTP / IMAP Medium Medium Corporate mail workflows Polling & credential maintenance
Mock SMTP Very High Very Fast Local integration tests Does not validate real deliverability
Webhooks High Very Fast Event-driven CI Requires webhook receiver infra

1. Dedicated Email API

An Email API gives your test runner programmatic access to test messages over clean HTTP endpoints. A typical flow is:

Create inbox → Get credentials → Trigger OTP → Query API → Receive email → Extract OTP → Continue browser test

This is the ideal approach for CI/CD because there is zero human interaction required.

2. SMTP and IMAP

SMTP and IMAP can be useful when you specifically need to test your organization's existing internal mail server infrastructure. However, they require complex credential management and polling sockets.

3. Mock SMTP

Mock SMTP is great for local development. The app sends an email to a local mock daemon (like MailHog), and the test inspects memory. It is fast, but it does not test real deliverability, DNS, or SPF/DKIM policies.

4. Webhooks

A webhook-based system notifies your test infrastructure the millisecond a message arrives. Instead of polling loops, the workflow is push-based:

Email arrives ↓ Webhook event ↓ Test receives notification ↓ OTP extracted

Which OTP Testing Approach Should You Choose?

  • For full CI/CD end-to-end testing, a dedicated Email API with isolated test inboxes is the gold standard.
  • For local integration testing, mock SMTP is simpler and faster on developer laptops.
  • For testing corporate mailbox workflows, SMTP/IMAP may be appropriate.
  • For high-speed event-driven pipelines, webhooks reduce polling latency.

Choose the approach based on what the test needs to prove. If the purpose is to verify the complete user verification journey, your E2E test must include the real email step.

How to Automate OTP Email Testing (6-Step Guide)

A resilient OTP automation workflow follows six distinct steps:

Step 1: Create an Isolated Test Inbox

Generate a unique email address for each test or CI worker: 

const workerIndex = process.env.TEST_WORKER_INDEX || "0";
const uniqueRunId = `${Date.now()}-w${workerIndex}`;
const testEmail = `test-user-${uniqueRunId}@sandbox.example.test`;

If your Email API supports disposable inboxes, create the inbox dynamically when the test begins and auto-delete it during teardown.

Step 2: Trigger the OTP Email

Use your browser automation framework to perform the user action:

await page.goto(`${BASE_URL}/register`);
await page.fill('input[name="email"]', testEmail);
await page.fill('input[name="password"]', process.env.TEST_PASSWORD);
await page.click('button[type="submit"]');

await expect(page.getByRole('heading', { name: /verify/i })).toBeVisible();

Step 3: Retrieve the Email

Use bounded polling with a timeout helper:

async function waitForEmail(inboxId, token, timeoutMs = 15000) {
  const start = Date.now();
  while (Date.now() - start < timeoutMs) {
    const response = await fetch(
      `${EMAIL_API_URL}/inboxes/${inboxId}/messages`,
      { headers: { Authorization: `Bearer ${token}` } }
    );
    if (response.ok) {
      const messages = await response.json();
      if (messages.length > 0) {
        return messages[0];
      }
    }
    await new Promise(resolve => setTimeout(resolve, 500));
  }
  throw new Error("Timed out waiting for OTP email");
}

Step 4: Identify the Correct Message

Filter messages using metadata: Recipient, Sender, Subject, and Test-specific IDs.

  • Recipient: otp-build123-worker0@example.test
  • Sender: no-reply@staging.example.com
  • Subject: Verify your email address

Step 5: Extract the OTP

Use labeled pattern matching with a resilient fallback:

function extractOtp(body) {
  const labeled = body.match(
    /(?:verification code|security code|otp|passcode)\s*(?:is|:|=)?\s*([0-9]{4,8})/i
  );
  if (labeled) {
    return labeled[1];
  }
  const fallback = body.match(/\b([0-9]{6})\b/);
  return fallback ? fallback[1] : null;
}

Step 6: Submit and Verify the OTP

Submit the extracted OTP back into the browser UI and assert success:

const email = await waitForEmail(inboxId, inboxToken);
const body = email.textBody || email.htmlBody || "";
const otp = extractOtp(body);

if (!otp) {
  throw new Error("OTP code not found in email");
}

await page.fill('input[name="otpCode"]', otp);
await page.click('button[type="submit"]');

await expect(page).toHaveURL(/dashboard/);
await expect(page.getByText(/welcome/i)).toBeVisible();

How to Test OTP Emails with Playwright

Playwright is ideal for OTP testing because browser actions and API requests integrate natively in the same test workflow. 

import { test, expect } from '@playwright/test';

test('user can verify email with an OTP', async ({ page }) => {
  const inbox = await createTestInbox();
  await page.goto(`${BASE_URL}/register`);
  await page.fill('input[name="email"]', inbox.email);
  await page.fill('input[name="password"]', process.env.TEST_PASSWORD);
  await page.click('button[type="submit"]');

  const message = await waitForEmail(inbox.id, inbox.token);
  const otp = extractOtp(message.textBody || message.htmlBody || '');
  if (!otp) {
    throw new Error('OTP not found');
  }

  await page.fill('input[name="otpCode"]', otp);
  await page.click('button[type="submit"]');
  await expect(page).toHaveURL(/dashboard/);
});

Keep mailbox creation, email retrieval, and OTP parsing in reusable helper modules to keep individual E2E tests clean and declarative.

How to Test OTP Emails with Cypress

In Cypress, use a custom command to interact with the Email API: 

Cypress.Commands.add('fetchOTP', (inboxId, token) => {
  return cy.request({
    method: 'GET',
    url: `${Cypress.env('EMAIL_API_URL')}/inboxes/${inboxId}/messages`,
    headers: {
      Authorization: `Bearer ${token}`
    }
  }).then(response => {
    const body = response.body[0]?.textBody || '';
    const match = body.match(
      /(?:verification code|otp|passcode)\s*(?:is|:|=)?\s*([0-9]{4,8})/i
    );
    if (!match) {
      throw new Error('OTP not found');
    }
    return match[1];
  });
});

How to Test OTP Emails with Selenium

Selenium controls the browser while a standard HTTP client (e.g., Python requests) handles email retrieval: 

import os
import re
import requests

def fetch_otp(inbox_id, token):
    response = requests.get(
        f"{os.environ['EMAIL_API_URL']}/inboxes/{inbox_id}/messages",
        headers={"Authorization": f"Bearer {token}"},
        timeout=15,
    )
    response.raise_for_status()
    body = response.json()[0].get("textBody", "")
    match = re.search(
        r"(?:verification code|otp|passcode)\s*(?:is|:|=)?\s*([0-9]{4,8})",
        body,
        re.I,
    )
    if not match:
        raise RuntimeError("OTP not found")
    return match.group(1)

Parsing OTP Emails Reliably

Email markup can contain tracking pixels, CSS rules, base64 images, and hidden elements. Searching raw HTML with a simple regular expression often yields false positives.

Prefer Structured Selectors

If you control your email templates, add a test attribute to the OTP container:

<span data-testid="otp-code">482913</span>

The test parser can query this exact DOM node, eliminating reliance on changing marketing copy.

Plain Text vs HTML Email

Plain Text: Clean and easy to parse with minimal regex ambiguity. 

Your verification code is 482913. This code expires in 10 minutes.

HTML: Rich formatting requires DOM parsing. Use Cheerio for Node.js: 

import * as cheerio from 'cheerio';

function extractOtpFromHtml(html) {
  const $ = cheerio.load(html);
  const explicit = $('.otp-code, #verification-code, [data-testid="otp-display"]')
    .first()
    .text()
    .trim();
  if (/^\d{4,8}$/.test(explicit)) {
    return explicit;
  }
  return extractOtp($('body').text());
}

Testing Magic Links

For magic links, retrieve the email, extract the link, and always validate the target hostname before navigation: 

function extractMagicLink(body, host) {
  const pattern = new RegExp(`https?://${host}/[^"\\s<]+`, 'i');
  return body.match(pattern)?.[0] || null;
}

Testing Resend, Expiration & Invalid OTPs

1. Testing OTP Resend

Verify that clicking Resend issues a new OTP and invalidates the previous code:

Request OTP A → Receive OTP A → Click Resend → Receive OTP B → Submit OTP B (Accepted) & Submit OTP A (Rejected)

2. Testing OTP Expiration

Do not sleep for 10 minutes in CI. Use a staging environment variable or mock clock with a 2-second expiration window to validate rejection behavior.

3. Testing Invalid & Reused OTPs

Submit an altered code (otp + "1") and verify clear error messaging. Also test single-use enforcement: submitting the same correct OTP a second time must fail.

How to Run OTP Tests in GitHub Actions & GitLab CI

Store API keys in CI secret vaults instead of committing them to code.

GitHub Actions Workflow

name: E2E OTP Tests
on:
  pull_request:
    branches: [main]

jobs:
  otp-tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - name: Run OTP E2E tests
        env:
          BASE_URL: ${{ secrets.STAGING_BASE_URL }}
          EMAIL_API_URL: ${{ secrets.EMAIL_API_URL }}
          EMAIL_API_KEY: ${{ secrets.EMAIL_API_KEY }}
          TEST_PASSWORD: ${{ secrets.TEST_PASSWORD }}
        run: npx playwright test

e2e_otp_tests:

Handling OTP Test Collisions in Parallel CI Jobs

When running 4–8 parallel workers, each worker must have an isolated email namespace: 

const worker = process.env.TEST_WORKER_INDEX || "0";
const build = process.env.CI_PIPELINE_ID || `${Date.now()}`;
const email = `otp-${build}-worker-${worker}@sandbox.example.test`;

Polling vs Fixed Delays

Avoid await sleep(5000). If delivery takes 400ms, 4.6 seconds are wasted. If delivery takes 6 seconds, the test fails falsely.

Use bounded polling with exponential backoff or short intervals (300–500ms) with a 15-second total ceiling.

Debugging & Safe CI Diagnostics

When a test fails, provide clear contextual diagnostics without logging sensitive auth tokens: 

OTP email was not found.
Inbox: ci-test-worker-2
Recipient: redacted@sandbox.example.test
Expected sender: staging-mail@example.com
Elapsed time: 15 seconds

Never log: OTP codes, passwords, magic links, or bearer tokens in test reports or screenshots.

Security and Data Cleanup

  • CI Secrets: Store EMAIL_API_KEY and passwords in protected secret stores.
  • Scoped Access: Use API tokens with permissions restricted solely to staging sandbox inboxes.
  • Automatic Teardown: Delete test users and disposable inboxes in a finally block.
  • Short TTL: Set mailbox retention to expire after 1 hour automatically.

Email API vs IMAP vs Mock SMTP Comparison

Method Best Use Advantages Trade-offs
Email API CI/CD E2E Programmatic access, isolated inboxes, webhooks External service dependency
IMAP Corporate mail testing Validates real mail servers Complex setup, connection limits
Mock SMTP Local unit tests Ultra fast, zero external calls No real DNS/deliverability verification

Common OTP Testing Problems and Fixes

Problem Likely Cause Recommended Fix
OTP not found Email still processing Use bounded polling helper with timeout
Wrong OTP selected Shared inbox between tests Assign a unique email per parallel worker
OTP expired Runner slow or clock lag Shorten retrieval time; configure staging clock
Parser matches wrong number Raw HTML contains zip/order ID Use DOM parsing or labeled regex pattern
CI exposes credentials Hardcoded secrets Move tokens to GitHub/GitLab Secrets
Test hangs indefinitely Missing retrieval timeout Enforce strict 15s max timeout on email fetch

A Simple CI Checklist for OTP Email Tests

  • ✅ Is the test executing against staging or sandbox mail infrastructure?
  • ✅ Does every parallel worker generate a unique email address?
  • ✅ Are Email API tokens stored exclusively in CI secrets?
  • ✅ Does the email retrieval helper enforce a strict timeout?
  • ✅ Does the parser reliably target the OTP code element?
  • ✅ Are raw OTP values and magic links excluded from CI logs?
  • ✅ Are temporary inboxes and test users purged in teardown?
  • ✅ Does the final assertion verify full dashboard authentication?

Frequently Asked Questions

What is OTP email testing?

OTP email testing verifies that an application generates, delivers, retrieves, and accepts a one-time password sent by email. Automated testing ensures every deployment validates the complete authentication flow.

How do you automate OTP verification?

Create an isolated test inbox, trigger the OTP flow, retrieve the email through an Email API or controlled mailbox, extract the code, submit it in the browser, and verify the resulting application state.

Can you test OTP emails without Gmail?

Yes. You can use dedicated Email APIs, temporary test inboxes, mock SMTP, corporate IMAP mailboxes, or webhook-based delivery. A personal Gmail account is not required.

How do you prevent OTP tests from interfering with each other?

Give each test worker or test run a unique email address or mailbox namespace. Never share a single static inbox across parallel CI workers.

How do you test magic links?

Retrieve the email, extract the application URL, validate the expected domain, open the link in the browser test, and verify the authenticated state.
